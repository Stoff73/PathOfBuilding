# Code standards

For Path of Building Community: Lua 5.1 on LuaJIT, run inside the SimpleGraphic host. Every phase of every plan is reviewed against these rules, as `AGENTS.md` sets out.

1. Keep it simple, do not overcomplicate. Simple means easy to follow, not fewest files.
2. Comments only when necessary. Every source file keeps its header: `-- Path of Building`, then `-- Module:` or `-- Class:` and one line on its job.
3. Be concise: a short README and no emojis.
4. IMPORTANT: avoid overly defensive code. Handle exceptions only when necessary. Validate what comes from outside: imported builds, pasted items, share codes, API responses, files. Inside the calculation code, trust the data and let a bug raise. `pcall` belongs at those edges only.
5. Tooling:
   - Lua 5.1 on LuaJIT only. Nothing from Lua 5.2 or later: no `//`, `&`, `|`, `<<` operators, `unpack` not `table.unpack`, and bitwise work through the `bit` library.
   - Run the tests with `docker-compose up`, which uses the CI image, or with `busted --lua=luajit`. Add `-p TestName_spec.lua` for one file. Every spec passes before a phase is ticked off.
   - Format as `.editorconfig` says: tabs in Lua. Match the file you are in, and never reformat or rename lines the change doesn't need.
   - CI spell-checks every changed file with cspell. Game terms it doesn't know go in its dictionary, not around it.
   - The Python scripts in the root, and `macos/package.py`, are release tooling: Python 3.10 or later, standard library only, fully type-hinted.
   - The C++ in `macos/` is C++17 and compiles without warnings under `-Wall -Wextra`. Its shell scripts are bash and start with `set -euo pipefail`.
6. Types and names:
   - Lua has no static types, so new shared functions and classes carry EmmyLua annotations: `---@param`, `---@return`, `---@class`.
   - Declare everything `local`. The only globals are the ones the program already shares, such as `main`, `launch`, `data`, `modLib` and `calcLib`. Adding one is a decision recorded in the plan.
   - Functions and variables are `camelCase`. Classes are made with `newClass`, named in `PascalCase`, and so are their methods.
   - Calculation modules cache the library functions they use at the top of the file (`local t_insert = table.insert`, `local m_floor = math.floor`). Follow it there.
7. Add a dependency only when it saves real work, and say why in the commit. There is no lockfile: libraries are vendored in `runtime/lua`. A new one is pure Lua, goes there, and has its licence added to `LICENSE.md`.
8. Game numbers live in data, never in code. Values from the game files are in `src/Data`. Tuning constants are in `data.misc` in `src/Modules/Data.lua`. A formula names them; it never repeats the literal.

## Project rules

9. IMPORTANT: never hand-edit a generated file. A file that starts `-- This file is automatically generated, do not edit!`, which is most of `src/Data`, is written by the scripts in `src/Export`. Change the script or its template, rerun the exporter, and include both the script and the data in the change. Skills are generated from the templates in `src/Export/Skills`.
10. IMPORTANT: `src/Data/ModCache.lua` always matches the parser. Any change to `src/Modules/ModParser.lua`, or to the text it parses, regenerates it with `cd src && LUA_PATH='../runtime/lua/?.lua;../runtime/lua/?/init.lua;./?.lua;./?/init.lua' REGENERATE_MOD_CACHE=1 luajit HeadlessWrapper.lua < /dev/null`, or `Ctrl` + `F5` in the app. The CI job `check_modcache` enforces this. Read the diff: a cached mod that changed and wasn't asked for is a regression.
11. IMPORTANT: every change to a number the program shows is proven by a spec. A change to `src/Modules/Calc*.lua`, the parser or mod data comes with a spec in `spec/System` that fails before the change and passes after it.
12. Builds saved by an earlier version keep loading. A change to what a build file holds also reads the old form.
13. Modifiers are written in the syntax of `docs/modSyntax.md` and parsed as `docs/addingMods.md` describes. Skills follow `docs/addingSkills.md`.
14. `manifest.xml`, `CHANGELOG.md` and `changelog.txt` are written by the release process in `RELEASE.md`. A feature change leaves them alone. The manifest with the `macos` entries, and `runtime-macos.zip`, are committed on the branch `macos-release` only; on every other branch `manifest.xml` stays as upstream has it.

## Organising the code

15. IMPORTANT: one module, one job. Each file does one thing, and its name says what. A new file over 200 lines is doing too much. Nothing checks this automatically yet, so the phase review does.
16. Many files predate rule 15: `ModParser.lua`, `CalcOffence.lua`, `ItemsTab.lua` and `CompareTab.lua` are each over 5,000 lines. Don't grow them with a new job. Behaviour with its own job goes in a new module beside them, as `CalcTriggers.lua` and `CalcMirages.lua` do. A change that belongs inside an existing function stays there. Splitting one of these files is its own brief, never a side effect of another change.
17. Keep these boundaries. Something new goes in the module for its job, or a new module named for it:
   - `src/Modules/Calc*.lua`: the calculation engine. It turns a build's modifiers into output numbers, and it draws nothing.
   - `src/Modules/ModParser.lua`: the only place that turns modifier text into mods.
   - `src/Modules/Common.lua` and `src/Modules/Utils.lua`: shared helpers. Look here before writing a new one.
   - `src/Classes/`: one class per file, the file named for the class. Controls are `*Control.lua` and tabs are `*Tab.lua`.
   - `src/Data/`: game data. Only `src/Export` writes the generated files in it.
   - `src/Export/`: the only place that reads the game's files.
   - `src/HeadlessWrapper.lua`: stands in for the graphics host so the program runs from the command line and under test. `src/_SimpleGraphic.def.lua` defines the host's API.
   - `runtime/`: the Windows host binaries and the vendored Lua libraries. Features don't edit it.
   - `macos/`: everything Mac-specific that we write: the launcher, the update helper, and the build and packaging scripts. `macos/SimpleGraphic` is our fork of the host, as a submodule; a change there is guarded so that it only affects macOS. `macos/build/` and `macos/runtime/` are build output and are not committed. The host's files keep the line endings they have, which for most is CRLF: an edit that rewrites them makes every line a change and the fork unmergeable.
   - `spec/System/`: the busted specs. `spec/TestBuilds/`: saved builds whose output is compared as a whole.
18. Tests mirror the code: `spec/System/Test<Name>_spec.lua` tests `<Name>`. A spec starts from `newBuild()` and drives the real build objects, not copies of their logic.
